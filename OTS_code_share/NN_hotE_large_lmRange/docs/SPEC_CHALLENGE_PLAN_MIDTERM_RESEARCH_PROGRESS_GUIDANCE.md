# 挑战计划中期考核“科研亮点工作 1”指导 SPEC

## 0. 文档状态与边界

- 状态：已由用户确认并于 2026-08-25 缩小材料范围，进入执行。
- 目标产物：一份面向“刚读博一、了解项目但从未填写中期考核材料”的导师式写作指导。
- 明确不做：不直接代写可提交的三页以上完整正文；不虚构实验、指标、图表、工作量或个人贡献；不把论文设想、历史快照和当前代码实现混为一谈。
- 默认输出语言：中文。
- 默认聚焦栏目：`三、科研工作进展 / （一）科研亮点工作 / 亮点工作 1`。
- 材料边界：以中期考核模板、出站报告和论文草稿为核心；代码仅用于核对科学术语、公式含义和基础方法流程，不作为撰写者阶段进展的主要证据。
- 明确排除：不纳入后续训练作业、Slurm/集群记录、后续模型指标、论文复现作业、canonical 流水线重构成果及其派生产物；这些内容发生在本次材料所对应的工作阶段之后，也不应被归入撰写者或其前辈当时已经完成的工作。
- 安全边界：不读取、展示、转述或纳入任何凭据文件内容；不读取与本任务无关的数据集、模型及其他大体量产物。

## 1. Requirements（需求）

### 1.1 功能目标

1. 找到并核对挑战计划中期考核模板，准确提取栏目要求、篇幅、字体、行距、图文规范及可能的上下文约束。
2. 建立与目标栏目直接相关的证据图谱，覆盖：
   - 中期考核模板；
   - 出站报告；
   - 论文草稿；
   - 出站报告和论文草稿中已经出现的图表；
   - 与上述两份材料所述方法直接对应的少量代码，仅作原理核对；
   - Git 当前动态状态与用户未提交修改。
3. 从“问题需求、主要进展、创新性或挑战性、价值贡献”四个指定角度，判断最适合作为“亮点工作 1”的叙事主线。
4. 以科研指导老师口吻解释：每一部分为什么写、写什么、从哪些证据中取材、哪些表述容易失真、怎样组织到不少于三页且不空泛。
5. 优先复用出站报告和论文草稿已有图表，给出图文安排、段落骨架、证据引用表、归属风险和下一步补证建议，但不生成完整可直接提交的正文。
6. 区分并明确标注：
   - 出站报告明确记录的阶段工作；
   - 论文草稿希望表达但可能仍需审慎措辞的科学主张；
   - 代码只能帮助解释、不能反向证明属于撰写者的内容；
   - 前辈/合作团队既有基础与撰写者本人贡献的归属边界；
   - 仍需用户确认的个人贡献与考核时间范围。

### 1.2 用户故事

作为一名刚读博一、熟悉项目内容但不熟悉考核材料写法的学生，我希望得到一位导师式助手的详细指导，使我能够：

- 选出真正能代表阶段性科研进展的一项亮点；
- 理解评审专家关心的逻辑，而不是罗列代码和工作日志；
- 用可靠证据支撑创新性、难点和价值；
- 规划至少三页正文中的图、表和段落比例；
- 最终用自己的语言完成材料，并能应对导师修改和中期答辩追问。

### 1.3 验收标准

- 指导必须覆盖模板原文要求的四个角度。
- 必须给出一个首选叙事主线，并说明为什么优于至少一个备选主线。
- 必须提供逐页或逐段写作结构，但不得展开成完整成稿。
- 必须提供至少一份“主张—证据—出处—风险”对应表。
- 必须给出建议图表清单，并说明每幅图回答什么科研问题、现有素材是否可直接使用。
- 所有定量结论都能追溯到仓库中的具体文件或现场核验结果；不确定项必须显式标注。
- 必须面向新手解释“科研进展”和“项目说明书/代码介绍”的区别。

## 2. Design（设计）

### 2.1 总体方法

采用“核心材料定位 → 出站报告与论文对读 → 代码最小核对 → 归属分层 → 亮点候选比较 → 评审叙事设计 → 图文骨架 → 风险与补证”的流程。

```text
模板约束 ───────────────┐
出站报告（工作事实）────┤
论文草稿（科学叙事）────┼→ 证据/归属矩阵 → 亮点候选比较 → 推荐叙事主线
少量代码（原理核对）────┤                                  ↓
报告/论文既有图表 ──────┘                             三页图文骨架
                                                          ↓
                                               新手写作指导与补证清单
```

### 2.2 架构决策

1. **证据优先，不按文件顺序复述。** 仓库材料按“问题、方法、实现、验证、价值”重组，避免写成开发日志。
2. **证据顺序固定。** 出站报告说明当时实际开展了哪些工作，论文草稿说明科学问题、方法逻辑和作者希望表达的贡献；代码只在两者出现术语或流程歧义时作最小核对，不能用后续实现覆盖历史材料。
3. **一个亮点只讲一条主线。** 默认优先考察“以低通 Fourier 表示缓解非 Maxwellian EVDF 的 OTS 反演病态性，并用神经网络实现快速重建”这一论文时期主线；不把后续训练工程、集群适配、重构或复现工作纳入亮点。
4. **图表承担论证功能。** 每幅图必须对应一个评审问题，例如“为何需要 Fourier 表示”“当前闭环完成到哪里”“模型性能如何”“边界和不足是什么”。
5. **不直接代写全文。** 输出采用提问、段落任务、证据提示、半成品句式和自检表，保留用户的科研判断和个人表达。
6. **简单优先。** 不引入新的复杂评价体系；候选亮点仅按相关性、证据强度、创新性、个人贡献可说明性、三页可展开性进行轻量比较。

### 2.3 数据模型

#### FileRecord

```text
path: 文件绝对路径或仓库相对路径
kind: template | paper | exit_report | source_reference | figure | other
status: readable | binary_metadata_only | excluded_sensitive | missing
relevance: high | medium | low
notes: 与亮点工作 1 的关系
```

#### EvidenceClaim

```text
claim: 可用于材料中的科研主张
evidence_type: exit_report_fact | paper_claim | code_background_only | attribution_needed
source_paths: 支撑文件列表
confidence: high | medium | low
risk: 可能的夸大、未验证、跨阶段借用或个人归因问题
recommended_wording: 建议采用的审慎表达方式
```

#### HighlightCandidate

```text
title: 候选亮点名称
problem_need: 所回应的科学或工程问题
progress: 已完成进展
innovation_challenge: 创新性与挑战性
value: 科学、方法或应用价值
evidence_strength: 证据强度
personal_contribution_gap: 尚需用户确认的个人贡献
recommendation: primary | secondary | reject
```

#### FigurePlan

```text
figure_id: 图号
question_answered: 该图回答的评审问题
source: 现有文件或建议新绘制的数据来源
placement: 建议页码/段落
caption_points: 图注必须说明的信息
availability: ready | needs_redraw | missing_data
```

### 2.4 分析流程接口与伪代码

以下是本任务的分析接口，不是对项目源码的修改。因本任务不新增程序功能，不存在需要写入仓库代码的生产函数。

#### `inventory_repository(root) -> list[FileRecord]`

用途：定位核心材料并记录排除边界，不再执行全仓内容审阅。

```text
输入 root
用 Git 状态与文件名枚举现场核对当前工作树
优先定位模板、出站报告、论文草稿及其图表
对候选文件：
    若为明确凭据文件：标记 excluded_sensitive，不读取内容
    若为模板、出站报告或论文：标记 readable，并完整核对相关页面
    若为源码：仅在直接对应论文方法时标记 source_reference
    若为训练作业、运行报告、模型、数据或后续产物：标记排除，不读取内容
返回 FileRecord 列表
```

#### `extract_template_constraints(template_files) -> dict`

用途：确认模板栏目、格式和相邻章节关系。

```text
定位中期考核模板
提取目标栏目原文与文档样式
核对字体、字号、行距、页数、图文要求
查看前后栏目，避免与“成果清单”“后续计划”等内容重复
返回约束字典和可追溯页码/位置
```

#### `build_project_evidence(records) -> list[EvidenceClaim]`

用途：把论文、报告、代码、测试和产物转换为可写入材料的证据主张。

```text
完整读取出站报告与论文，提取研究问题、方法主张、当时结果和既有图表
仅在必要时读取直接相关代码片段，解释 Fourier 表示、OTS 正向关系或网络输入输出
不读取测试、训练作业、集群报告或后续定量结果
对每条潜在主张：
    标注证据类型与来源
    检查出站报告与论文之间的范围差异
    检查该工作属于前辈/合作团队基础还是撰写者本人可认领贡献
    给出置信度、归属风险和审慎措辞
返回 EvidenceClaim 列表
```

#### `compare_highlight_candidates(evidence) -> list[HighlightCandidate]`

用途：比较可作为“亮点工作 1”的几条叙事主线。

```text
从证据中聚类出 2–4 个候选主题
逐一检查：问题是否明确、进展是否阶段性完整、创新是否有依据、价值是否可说明
评估三页展开能力与图表支持
识别必须由用户确认的个人贡献
排序并选择 primary 候选
返回候选列表及选择理由
```

#### `design_three_page_outline(primary, evidence) -> dict`

用途：生成不少于三页的图文写作骨架，而非完整正文。

```text
第 1 页安排问题背景、需求和总体思路
第 2 页安排核心方法、主要进展和技术挑战
第 3 页安排验证结果、创新价值、局限与阶段结论
为每一页分配段落任务、建议字数和图表
给出段落之间的因果连接
返回逐页骨架
```

#### `plan_figures(primary, records, evidence) -> list[FigurePlan]`

用途：选择现有图或提出重绘建议。

```text
枚举与主线直接相关的出站报告图片和论文图
逐图判断清晰度、事实状态、是否适合考核材料
优先选择流程图、方法示意图、定量结果图和边界/泛化图
若现有图不适用，说明需要从哪些已有数据重绘
返回 FigurePlan 列表
```

#### `produce_advisor_guidance(outline, evidence, figures) -> guidance`

用途：输出面向博一新手的导师式指导。

```text
先解释评审者阅读该栏目的判断逻辑
再给出推荐标题与一句话中心论点
逐段说明写作任务、可用证据、常见错误和自问问题
加入有限的句式模板，但不串联成完整正文
附图表方案、主张证据表、风险表和补证清单
返回 guidance
```

#### `validate_guidance(guidance, constraints, evidence) -> validation_report`

用途：在交付前检查完整性与真实性。

```text
检查四个指定角度是否均覆盖
检查是否达到三页可展开性但未代写全文
检查所有数字是否有来源
检查论文意图、当前实现和历史结果是否分层
检查是否泄露凭据或把未验证主张写成事实
检查是否明确指出需要用户确认的个人贡献
返回通过项、风险项和待确认项
```

### 2.5 技术选型

- 文件与代码检索：优先使用 `rg` / `rg --files` 和只读 Git 命令；代码检索严格限于解释报告/论文中的方法。
- PDF：按 PDF 技能进行文本提取、页面渲染和必要的视觉核对。
- DOCX：按文档技能读取结构与样式，必要时渲染页面核对模板版式。
- PPTX/图片：只读取出站报告、论文或模板直接引用的相关素材；视觉检查用于判断可读性。
- 多智能体分工：模板/出站报告与论文/研究叙事分别核查；代码核对由主智能体控制在最小范围内，主智能体负责统一证据标准和最终指导。

## 3. Tasks（任务拆解）

1. **T0 — SPEC 确认**（无依赖）
   - 用户确认本 SPEC 的范围与默认主线探索方向。
2. **T1 — 动态状态与核心材料定位**（依赖 T0）
   - 核对 Git 状态；定位模板、出站报告、论文草稿；记录但不读取训练/后续产物；保护用户未提交修改。
3. **T2 — 模板与出站报告核查**（依赖 T1）
   - 定位并读取模板、出站报告；提取目标栏目与可迁移的科研叙事。
4. **T3 — 论文草稿核查**（依赖 T1，可与 T2 并行）
   - 提取研究问题、方法、创新、当时结果、局限及论文未完成项。
5. **T4 — 最小代码核对**（依赖 T2/T3）
   - 只核对报告/论文中关键方法术语和基础流程，不提取后续训练或工程进展。
6. **T5 — 既有图表筛选**（依赖 T2/T3）
   - 只从出站报告和论文草稿筛选适合中期材料的图表。
7. **T6 — 建立主张—证据—归属矩阵**（依赖 T2–T5）
   - 合并范围差异、标注置信度与归属，识别不可直接使用的夸大或跨阶段表述。
8. **T7 — 比较亮点候选并选择主线**（依赖 T6）
   - 给出首选与备选主题、优劣和适用条件。
9. **T8 — 设计三页图文骨架与图表方案**（依赖 T7）
   - 逐页、逐段、逐图说明写法和取材来源。
10. **T9 — 输出导师式指导与新手自检表**（依赖 T8）
    - 不代写全文；加入答辩追问、常见误区和需用户补充的信息。
11. **T10 — 验收核查**（依赖 T9）
    - 对照模板约束和本 SPEC 出具完成性检查。

## 4. Acceptance Criteria / Tests（验收标准）

### 4.1 材料覆盖检查

- 有核心材料定位结果，并明确记录训练作业、后续代码更新、模型/数据和敏感文件的排除边界。
- 模板与出站报告均有明确定位和内容核对记录。
- 代码只在论文/报告原理解释确有需要时作少量核对，不以当前实现或后续结果填充中期材料。
- 不核验或引用训练作业、远端状态、后续模型性能和复现结果。

### 4.2 科研叙事检查

- 推荐主线能用一句话说明“解决什么问题—采用什么关键思想—做到什么阶段—有什么价值”。
- 四个模板维度不是四段孤立罗列，而是构成因果链。
- 主要进展忠实于出站报告和论文草稿对应时期，也诚实呈现局限和下一步，不把前辈、团队或后续工程工作包装成撰写者个人发现。
- 创新性区分“方法创新、实现创新、验证创新、工程贡献”，并只选择证据充分的类别。

### 4.3 图文与篇幅检查

- 至少给出 3 页可展开骨架，每页有中心任务、建议篇幅和图表位置。
- 建议图表不少于 3 类：问题/流程图、方法或数据表示图、定量验证图。
- 每幅图都附带“它证明什么、来自哪里、需不需要重绘、图注写什么”。
- 版式建议符合 4 号宋体、26 磅行距和图文并茂要求。

### 4.4 真实性与边界检查

- 所有数字、作业结果和性能结论可追溯。
- 不将论文中的 `[ref]`、`check!` 或未复核声明写成确定事实。
- 不引用后续训练、独立复现、集群运行或 canonical 重构内容。
- 不读取或泄露凭据；不改动用户代码、模板或报告。
- 最终交付不是完整代写稿，而是一份足以让用户独立完成写作的详细导师指南。

## 5. 已确认范围与仍需补充的信息

1. 已确认首选探索方向限于出站报告和论文草稿对应阶段；不纳入后续训练/评估闭环、Figure 3 复现、集群作业或工程化流水线更新。
2. 已确认代码仅作参考，用于核对关键科学概念和早期方法流程，不能作为阶段工作归属证据。
3. 撰写者本人、其前辈与合作团队之间的具体贡献分工，以及考核统计截止日期，若核心材料中无法查明，将在最终指导中列为必须由用户确认的信息，不擅自归因。
